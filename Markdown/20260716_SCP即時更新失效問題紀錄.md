# SCP 即時更新失效問題紀錄（客戶端需 F5）

> 日期：2026-07-16
> 環境：客戶端部署機（SQL Server `192.168.4.241\SQLEXPRESS`，DB `agvDB_1400004`）
> 狀態：**已修復並驗證通過**
> 關聯：2026-06-05 首次客訴（當時未解）、ToDo `20260605_SCP即時更新Service硬化`

---

## 1. 症狀

- 資料庫變更後，SCP 所有畫面（庫位、AGV 位置、任務列表、電量）都不會即時更新，必須手動 F5。
- 開發機完全正常，僅客戶端部署機異常。
- 自 2026-06-05 首次客訴以來持續未解。

## 2. 背景 — SCP 即時更新鏈路

```
DB 資料變更
  → SQL Server Query Notification（Service Broker）
  → WebGui/SCP/Services/Service.cs 註冊的 6 條 SqlDependency 觸發
  → SignalR (/CommonHub) 廣播 6 個事件（SendTracChange 等）
  → 前端 js 收到事件後呼叫對應 API（如 /api/Common/UpdateTrac）重繪畫面
```

鏈路任一節斷掉，畫面就停在舊狀態，且多數斷點為靜默失效。

## 3. 診斷過程（逐項排除）

| # | 檢查項 | 結果 | 判定 |
|---|--------|------|------|
| 1 | `is_broker_enabled` | **1** | ✅ Broker 有開（排除 6/5 的假設根因） |
| 2 | 擁有者 `SUSER_SNAME(owner_sid)` | `DESKTOP-0TLF04I\MyUser` | ⚠️ 當下誤判為正常（見 §6 陷阱） |
| 3 | mcs 帳號 `SUBSCRIBE QUERY NOTIFICATIONS` 權限 | 1（且 mcs = dbo、db_owner） | ✅ 權限足夠 |
| 4 | `sys.dm_qn_subscriptions` 活訂閱數 | **6**（與 Service.cs 註冊數一致） | ✅ 訂閱建立正常 |
| 5 | `sys.transmission_queue` | 多筆卡死訊息（2025-11-10、11-18） | 🔴 遞送層曾失敗 |
| 6 | 失敗訊息全文 | **Error 15517**：`Cannot execute as the database principal because the principal "dbo" does not exist...` | 🔴 dbo 模擬失敗 |
| 7 | 同值更新實測（見 §4） | `transmission_queue` 立即新增 **2026-07-16 06:47:21** 的 15517 失敗列 | 🔴 **證實病灶現行發作** |

### 決定性實測手法（零風險）

```sql
-- 值完全不變、不影響調度邏輯，但 Query Notification 一樣觸發
UPDATE dbo.oPort SET HaveFlag = HaveFlag
WHERE StationNo = (SELECT TOP 1 StationNo FROM dbo.oPort WHERE UseFlag = 'Y');

-- 立刻檢查有無「當下時間戳」的新失敗列
SELECT TOP 5 enqueue_time, transmission_status
FROM sys.transmission_queue
ORDER BY enqueue_time DESC;
```

## 4. 根因

**客戶端 DB 由開發機備份還原，資料庫擁有者 SID 為別台機器的 Windows 帳號，
在客戶端 SQL Server 執行個體上不是有效登入。**

Service Broker 在「送出通知」那一刻需要 `EXECUTE AS dbo`，擁有者無效 → **Error 15517**
→ 通知永遠送不出去，卡死在 `sys.transmission_queue`。

### 為什麼拖了一個多月才抓到 — 三層假象

1. **`is_broker_enabled = 1`**：6/5 唯一的假設（broker 沒開）在此機不成立。
2. **訂閱建得起來（6 筆）**：建訂閱不需模擬 dbo，DB 端看起來一切健康。
3. **失敗訊息停在 2025-11**：QN 訂閱是一次性的，觸發失敗後即被消耗；SCP 收不到通知
   就不會重新註冊，鏈路整條靜默——之後連「新的失敗證據」都不再產生。
   （現存 6 筆活訂閱是後來網站重啟時重新註冊的，重註冊後尚未被觸發過。）

## 5. 修復（2026-07-16 執行，三步）

```sql
-- 1) 改資料庫擁有者為本機有效登入（瞬間生效、不踢任何連線）
ALTER AUTHORIZATION ON DATABASE::[agvDB_1400004] TO sa;
```

2) IIS 回收 SCP 應用程式集區 → 6 條訂閱重新註冊。

3) 同值更新實測驗證：
   - 瀏覽器 F12 Network 觀察到 `UpdateTrac` 請求 ✅
   - 畫面 1~2 秒內即時重繪 ✅
   - `sys.transmission_queue` 不再新增失敗列 ✅

### 收尾（選擇性）— 清除佇列殭屍訊息

```sql
DECLARE @h uniqueidentifier;
WHILE EXISTS (SELECT 1 FROM sys.transmission_queue)
BEGIN
    SELECT TOP 1 @h = conversation_handle FROM sys.transmission_queue;
    END CONVERSATION @h WITH CLEANUP;
END
```

## 6. 經驗與陷阱

- **⚠️ `SUSER_SNAME(owner_sid)` 查得到名字 ≠ 擁有者有效。**
  Windows 能解析該 SID（回傳帳號名）但該帳號非本執行個體的登入時，`EXECUTE AS dbo` 照樣 15517。
  正確判法：owner_sid 是否存在於 `sys.server_principals`，或直接看 `transmission_queue`。
- **QN 訂閱一次性 + 遞送失敗 = 雙重靜默**：既收不到通知、也不會持續留下新證據，
  是此類問題最難從現象反推的原因。
- **同值更新（`SET 欄位 = 欄位`）是零風險的 QN 觸發器**，適合在產線環境做端到端實測。

## 8. 快速診斷 SOP（供下次同症狀使用）

```sql
-- ① Broker 是否啟用 + 擁有者
SELECT name, is_broker_enabled, SUSER_SNAME(owner_sid) AS owner_login
FROM sys.databases WHERE name = N'<DB>';

-- ② 連線帳號權限（在該 DB 內、以應用程式帳號執行）
SELECT HAS_PERMS_BY_NAME(DB_NAME(), 'DATABASE', 'SUBSCRIBE QUERY NOTIFICATIONS');

-- ③ 活訂閱數（SCP 網站運行中，正常 = 6）
SELECT COUNT(*) FROM sys.dm_qn_subscriptions WHERE database_id = DB_ID();

-- ④ 遞送佇列失敗訊息（15517 = 還原 DB 擁有者問題）
SELECT TOP 20 enqueue_time, transmission_status
FROM sys.transmission_queue ORDER BY enqueue_time DESC;

-- ⑤ 零風險端到端實測（同值更新）＋ 回查 ④ 有無新失敗列
UPDATE dbo.oPort SET HaveFlag = HaveFlag
WHERE StationNo = (SELECT TOP 1 StationNo FROM dbo.oPort WHERE UseFlag = 'Y');
```

判定表：①=0 → 開 Broker；③=6 且 ④ 有 15517 → `ALTER AUTHORIZATION`；
①③④ 全正常 → 嫌疑轉前端 SignalR（瀏覽器 F12 Console/Network 查 Hub 連線）。
